## 2. A · 工作空间与工程化（20.5 / 25）

### 做得好的

1. **分层是真分层的，不是摆设**：`src/team01/`（库）+ `src/scripts/`（阶段脚本）+ `dashboard/`（展示）
   + `tests/`（守卫）+ `config/project.yaml`（唯一参数源）+ `Makefile`（单入口）。这条线走得比多数课程项目远。
2. **双模式防呆**：`TEAM01_MODE=sample|full` 让 60k 行的合成固定样本和 61.7M 行真实面板走同一套代码，
   且 `sample` 模式下页面会打"这是合成数据"的横幅——**防止把 fixture 当结果**，这是很多人翻车的地方。
3. **真实数据真的跑过**：`data/raw` 3.0 GB、`data/interim` 1.6 GB、`data/processed/flights.parquet` 1.7 GB，
   `data/checksums.sha256` 在。不是"声称跑过"。
4. **7 个 notebook 全部有执行输出**（execution_count 与 outputs 都在），不是空壳。
5. **产出可追溯**：`outputs/` 下 12 张 CSV + 5 个 JSON 指标文件，`figures/` 14 张 300 dpi 图，
   每个数字都能指到一个文件。
6. **文档体量惊人**：26 份 markdown，约 3,976 行，含代码规范、命名规范、可视化规范、审计报告、中文对照、论坛文案、提交清单。

|---|---|---|
| **没有 git 仓库，但全流程都在讲 git** | 高 | 项目根有 `.gitignore`，README 讲"excluded from version control"，`submission-checklist.md` 第 6 条要求 `tag submission-v1`——但 `git status` 会一路走到用户家目录，说明**根本没有 `.git`**。这条清单项目前是**无法执行**的。课程明确 individual contribution，没有提交历史，"谁做了什么"只能靠文档自述。 |

## 3. B · 代码质量（17.0 / 20）

### 做得好的

1. **测试测的是"主张"，不是"语法"**——这是最难得的一点。看名字就知道：
   `test_waffle_allocates_exactly_one_hundred_cells`（蜂窝图必须正好 100 格）、
   `test_classifier_beats_a_coin_flip_only_barely`（分类器只允许"勉强"胜过抛硬币）、
   `test_validate_rejects_a_corrupted_table`（校验必须能拒绝坏数据）、
   `test_fixture_paths_never_shadow_downloaded_files`（固定样本不能影子掉真数据）。
   **实测 53 passed / 17.61 s**，与 README 声明一致。
2. **配置里写的是"取舍"，不是"参数"**。`config/project.yaml` 里 `tail_rows: 100000` 的注释直接给了
   性能论证（30k 行 36 s、100k 行 409 s、p90 系数在 100k 后不再移动）；`origin_top_k: 50` 给了收敛论证
   （350 个哑变量会让 IRLS 分位数回归不收敛）。这种注释是给"下一个接手的人"写的。
3. **7,709 行 Python，29 个文件，模块边界干净**：`config / schema / clean / io / attribution / tail / cluster / features / models / viz`。
4. **分层可测设计**：`create_app()` 可导入、`data_access` 有 `lru_cache`、
   `test_dashboard_figures_build_without_a_server` 让图表构建不需要起服务就能测。
5. **统计口径写进代码**：归因阈值 15 分钟、疫情年份单列哑变量、bootstrap 400 次按天重采样——
   这些都是"会被追问的细节"，被固化成代码而不是口头承诺。

### 扣分项（-3.0）

| 问题 | 严重度 | 说明 |
|---|---|---|
| `src/scripts/*` 阶段脚本没有直接单测 | 中 | 库层被测得很全，但 7 个入口脚本的参数解析、写盘路径、幂等性只靠 `make smoke` 跑一次。脚本层出错不会被 pytest 抓到。 |
| 无 CI | 中 | "53 passed" 目前只是本地事实。加一个 GitHub Actions（或哪怕 `make verify` 打印环境+测试+页数）就能变成可审计事实，成本 20 分钟。 |
| `viz.py` 823 行是单体 | 低 | 已经超过"一个文件一件事"的边界，建议按 `waffle / lorenz / cascade / map` 拆 4 个模块。 |
| 少量关键常量散落在两处 | 低 | 聚类稳定性 0.70 这条线，`config` 里没有，`captions.py` 与 `cluster.stability()` 各写一次（虽有注释说明必须同步）。 |

## 4. C · 网页 / 仪表板（16.5 / 20）

### 实测记录（今天现跑，不是看旧截图）

| 项 | 结果 |
|---|---|
| 启动 | `TEAM01_MODE=full`，加载 1.7 GB parquet，**1 分 46 秒**才 ready |
| 控制台 | **0 error / 0 warning** |
| 横向溢出 | 1440 px → **0 px**；390 px → **0 px** |
| 筛选联动 | 选 2020 年 → 航班数 400,000→**28,494**，均值 +4.5→**−5.3 min**，60+ 延误 6.2%→**2.8%**（COVID 年，方向正确）|
| 服务端 | 全部 `POST /_dash-update-component` 返回 **200** |

### 做得好的

1. **结构是"论证"不是"看板"**：页头 → KPI → "What the data says"（三句结论）→ 八块证据 → 乘客三条建议 → 方法卡 → 局限。
   读者不点任何按钮也能读完整个论证。
2. **面板标题是结论**（"The airline controls most of the delay"），不是变量名（"Carrier comparison"）。八个标题连起来读就是全文摘要。
3. **无障碍做了**：`<html lang="en">`、每个画布外包一层带 aria 标签的容器、KPI 有 label/note 两层文字。
   多数学生作业不会想到"八个没有无障碍名称的画布等于八个哑巴面板"。
4. **空数据 / 数据缺失有降级**：`DataUnavailable` 有明确提示 + 给修复命令；空帧时 caption 退回一句兜底话。
5. **坦白局限**：方法卡写了阈值口径、聚类 ARI 0.69 未过 0.70 线、AUC 0.685 的天花板。这是加分项。

## 8. 如果我是老师，我会问这 8 个问题

提前准备的答案会直接决定口头汇报分数：

1. **"页头写 61,689,698，KPI 写 400,000，哪个是真的？"** —— P0-1，答不上来会连带怀疑其他数字。
2. **"官方说平均延误 7 分钟，你说 +4.5 分钟，为什么？"** —— 正确答案是：7 分钟是 BTS 公布口径（含未完成航班），
   你对"已完成航班"算得 +4.5；两个口径不同，不是算错。（这一点提案里写了，但要能张口说）
3. **"73.3% 的置信区间怎么算的？重采样单位是什么？"** —— 按天 bootstrap，3653 天，400 次，CI 73.01–73.64。
4. **"聚类 ARI 只有 0.69，没过你自己定的 0.70，你为什么还叫它 archetype？"** —— 已经主动降级为"弱原型、仅供参考"，
   这个回答是对的，别临场改口说"其实很稳"。
5. **"AUC 0.685 比随机好多少？基线是多少？"** —— 基线 6.2% 正例率；这是排序能力，不是到达时间承诺。
6. **"'航司控制 73%' 是不是把相关当因果？"** —— 要明确：这是 BTS 的归因字段，不是我们做的因果推断；
   观测数据支持排序，不支持因果（提案已写明）。
7. **"六个人分别做了什么？有证据吗？"** —— 目前只有文档声明；有 git 历史才硬。
8. **"15 页你只用了 10 页，为什么？"** —— 建议准备一个"如果给我 15 页我会加什么"的答案（见 §5 可改进）。
