# Naming conventions

A name is the cheapest documentation there is. These rules exist so that a file
can be found from memory, and so that a figure can be traced to the stage that
produced it.

---

## 1. Directories

Lowercase, hyphenated, no spaces, no version suffixes.

```text
config/  data/  docs/  src/  notebooks/  dashboard/  figures/  outputs/  tests/  reports/
```

`data/` is further split by lifecycle, not by subject: `raw/` (untouched
downloads), `interim/` (partly processed), `processed/` (analysis-ready),
`sample/` (fixture). A file never moves backwards through that order.

---

## 2. Files

| Kind | Pattern | Example |
|---|---|---|
| Python module | `snake_case.py` | `features.py`, `attribution.py` |
| Stage script | `NN_verb_noun.py`, two-digit stage | `04_tail.py`, `05_clusters.py` |
| Notebook | `NN_Verb_Noun.ipynb` | `03_Delay_Attribution.ipynb` |
| Figure | `NN_topic.png` | `05_lorenz.png` |
| Output table | `topic_by_dimension.csv` | `cascade_by_hour.csv` |
| Metrics file | `stage.json` | `models.json` |
| Document | `NN_Title_With_Underscores.md` | `01_Team01_Meeting_Minutes.md` |

The two-digit prefix is the order of appearance, not the date. Figures are
numbered to match the order they are referenced in the report, so `figures/`
reads like the document.

---

## 3. Python identifiers

- Functions and variables: `snake_case`. Classes: `PascalCase`. Constants:
  `UPPER_SNAKE_CASE`.
- Booleans read as assertions: `is_rotation`, `has_cause`, `allow_cross`.
- No abbreviations except the domain's own: `crs` (computer reservation system),
  `nas` (national airspace system), `p90`, `arr`/`dep`. `df` is acceptable inside
  a function that only handles one frame; `data`, `frame`, `panel` are preferred
  at module boundaries.
- A function that returns a number is named for the number (`share_internal`); a
  function that returns a table is named for the table (`carrier_table`); a
  function that draws is prefixed `fig_`.

---

## 4. Data columns

`snake_case`, unit in the name where the unit is not obvious, no duplicates of
the table name.

| Good | Bad | Why |
|---|---|---|
| `arr_delay` | `ArrDelay` | The raw BTS name lives only in `schema.RENAME` |
| `min_late_aircraft` | `LateAircraftDelay` | `min_` prefix marks a minute measure |
| `share_delayed_60` | `pct60` | Says what is counted |
| `sched_dep_dt` | `dep` | Says it is scheduled, says it is a datetime |
| `n_dep` | `count` | Says what is counted |

Aggregated columns that are produced by a `groupby` are named for the statistic:
`mean_arr_delay`, `p90_arr_delay`, `share_internal`.

---

## 5. Git

Branches: `stage/<short-name>` (`stage/05-clustering`), `fix/<short-name>`,
`docs/<short-name>`. One branch per task, reviewed before merge.

Commits are imperative and say what changed and why:

```text
Add bootstrap interval to the family split

A single-year share has no uncertainty attached and a reader cannot tell a
2020 break from sampling noise. Resampling whole operating days keeps the
interval honest about day-level clustering.
```

No commit contains a figure that cannot be regenerated by a stage script.

---

## 6. What is never renamed

1. **BTS published fields.** They appear once, in `schema.RENAME`. Renaming the
   mapping is fine; renaming a raw field is not.
2. **Figure numbers.** `figures/05_lorenz.png` keeps its number even if the figure
   moves within the report; renumbering breaks every reference in the text.
3. **Stage numbers.** `04_tail.py` stays `04` even if an earlier stage is
   removed, because the numbers are referenced in the README and the minutes.
