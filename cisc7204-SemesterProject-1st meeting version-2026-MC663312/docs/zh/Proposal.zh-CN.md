## 1. 项目概述与研究问题

本提案记录一项**已完成**的端到端、可复现的美国国内航空延误分析，分析对象为**完整的十年面板**。**地理区域为美国，领域类别为商业航空运输。** 分析覆盖美国运输统计局（BTS）2015–2024 年十份年度文件，共 **63,079,392 行**，其中 **61,689,698 条为 20 家报告承运人的完成航班**，并与机场参考元数据关联。项目完成五件事：把延误分钟归因到 BTS 公布的**五类原因**；度量延误如何在同一运营日内被**继承传递**；把机场划分为不同的**延误风险原型**；对影响延误时长与严重延误风险的因素进行**排序**；并通过**联动式分析仪表板**与面向非专业读者的**叙事网页**把结论传达出去。

本工作扩展了 Assignment 02 阶段完成的试点（只用 2024 年单年数据）。单年数据无法把结构性规律与一次性运营冲击区分开、无法支撑稳定的聚类估计、也无法检验"航司可控 vs 系统强加"的拆分是否随时间成立。十年面板消除了这些局限：头条拆分为 **73.3% 航司可控、26.7% 系统强加**（bootstrap 95% 区间 73.0–73.6%），且在整个十年内稳定——逐年的内部份额范围从 69.7%（2018）到 77.4%（2022），摆动 7.7 个百分点。

航班延误是一个**公共利益问题**，因为一个平均值掩盖了差异极大的真实体验：旅客想知道"我这趟会不会废掉一个下午"，航司与监管方想知道"延误分钟到底从哪儿来"。因此我们把原因构成、典型延误、严重延误风险、日内传播与因素排序当作**彼此独立的问题**分别回答，而不是压成一个头条数字。

**研究问题**

- **RQ1** 已报告的延误分钟在 BTS 五类原因之间如何分布？这一构成在 2015–2024 年间的稳定性如何？
- **RQ2** 某一小时观测到的延误中，有多大比例是从同一架飞机当天更早的航段继承而来的？这种级联在哪些机场最集中？
- **RQ3** 当把规模与原因构成同时纳入考虑，美国机场是否能分成彼此不同的延误风险原型？区分它们的运营特征是什么？
- **RQ4** 给定航线、起飞小时与月份，延误风险能被多好地**排序**？一个联动式网页工具能否让非专业用户据此采取行动？

> **图 1** 十年面板延误分钟的归因：**73.3% 航司可控、26.7% 系统强加**（每格 = 1%；内部成因是 39% 前机晚到 + 35% 承运人，系统成因是 21% 空管 + 5% 天气）。

*关于数字的说明：本提案引用的每一个经验数值都算自**已完成的十年面板（2015–2024）**，并直接取自流水线的 `outputs/` 产物——61,689,698 条完成航班、73.3% 拆分、Gini 0.876、R² = 0.022、留出集 AUC = 0.685。一套 53 个测试钉住了每个数字的来源；本提案没有任何一张图是合成数据的结果。*

## 2. 项目目的

**学习成果。** 本项目对接三项课程学习成果：为不同的数据结构与问题选择适配的视觉编码；从探索性描述推进到有恰当限定的统计比较；为非专业受众设计交互式沟通产品。项目同时产出一个可用于作品集的端到端数据项目范例——从公开数据获取到可复现交付。

**技能。** 我们训练规模化数据工程（多文件摄入、分区存储、模式校验）、探索性分析、面板回归与稳健回归、分位数与逻辑回归建模、无监督聚类、带模型解释的梯度提升预测、仪表板与叙事网页开发、可复现性测试，以及简洁的技术写作。协作层面还包括代码评审、任务跟踪，以及把六人工作量按分析阶段切分。

**知识。** 项目培养对以下内容的实际理解：BTS 延误原因分类体系、15 分钟报告阈值、均值行为与尾部行为的差别、增量解释力、观察性模型的边界，以及聚类在什么条件下才真正有信息量、而不是特征缩放造成的假象。

## 4. 数据背景：区域、领域类别与来源

**地理区域。** 美利坚合众国——50 个州加哥伦比亚特区，包含阿拉斯加、夏威夷，因此跨越**四个时区**。描述性背景的时间窗为 2007–2024 年，分析面板为 **2015–2024 年**。美国海外领地（波多黎各、关岛、美属维尔京群岛）以及所有国际航段**均被排除**，因此每一行都描述一个"从美国机场起飞、并在美国机场降落"的定期国内客运航班。结论按三个嵌套空间层级报告：**全国**（全部航班）、**州**（起飞州）、**机场**（起飞机场）。

**领域类别。** 交通——商业航空，具体为**航空公司运营与空中交通绩效**。用数据科学的语言说，这是一个"定期运输网络上的运营绩效分析"问题：观测单位是**一个航段**，关心结果是**到达延误分钟数（及其厚尾）**，候选驱动因素是执飞承运人、两端机场、该航段在飞机当日排班中的位置、日历以及地面气象。

## 5. 方法概要

**数据获取与校验。** 每年 12 个月度文件拼接、类型强制转换、保留分析列。逐年检查行数、重复键、缺失率与阈值覆盖率后再写入分区 Parquet。完整面板通过：63,079,392 行、重复行为 0、阈值以上原因覆盖率 99.9999%。

**归因与稳定性。** 把已报告的延误分钟归入"航司可控"（承运人与前序航班晚到）与"系统强加"（空管、气象、安检）两类。构成按年重算，头条拆分附 bootstrap 区间。结果——**73.3% 内部、95% CI 73.0–73.6%**——在十年内稳定。

**尾部与集中度。** 在报告严重延误占比的同时报告均值、中位数与分位数；用 Lorenz 曲线与类基尼统计量刻画集中度。均值（+4.5 分钟）远高于中位数（−6.0 分钟），Gini 指数 0.876，试点的"均值 vs 尾部"假设在**面板上**得到确认。

**级联度量。** 继承延误用 BTS 前序航班晚到原因分钟与同机相邻航段的周转缓冲计算。结果把 38.8% 的前机晚到占比转成日内机制：6.0% 的航班处于有正向延误的飞机周转中，其中 17.1% 的延误分钟是继承来的。

**机场原型。** 机场用特征矩阵描述（均值、p90、严重延误占比、五类原因占比、季节振幅、起飞量、枢纽层级）。特征标准化后 k-means 按轮廓系数选 k，Ward 链接交叉验证，PCA 二维投影展示。选定解为 **k=5、195 机场、轮廓系数 0.2045**，并如实标注**不稳定**（平均 ARI 0.69，低于 0.70 阈值）。

**预测与解释。** 逻辑回归基线与梯度提升分类器预测"到达延误 ≥60 分钟"，按时间切分。SHAP 式重要性排序因素，依赖图暴露起飞小时曲线。留出集 **AUC 0.685（逻辑）/ 0.691（GBM）**，基础率 6.1%；全模型 R² 0.022。起飞小时是最强因素，占排序重要性 49.9%。

**制度控制。** 十年窗口装着两套运营制度，因此日历以控制变量而非发现进入每个模型：年份固定效应吸收长期趋势，疫情哑变量覆盖 2020 年 3 月至 2021 年 12 月。每一项头条统计都以"剔除这两年"重算，报告呈现**移动幅度**而非挑一版平均值。

**视觉设计与交互。** 图表按"它回答什么问题"来选择，遵循第 6 节的编码有效性排序。沟通层把**分析型仪表板**与**叙事页**分开：仪表板支持自由探索，叙事页按固定顺序带非专业读者走完四项发现。

## 6. 可视化设计依据

因为这是一门可视化课程，**每一张图都被当作一个需要论证的决策，而不是默认选项**。我们采用 Cleveland 与 McGill（1984）、Mackinlay（1986）的编码有效性排序：**共同尺度上的位置**读取最准确，其次是长度、角度与斜率，**面积与色相**读取最不准确。因此每张图都按它要回答的问题来选型；当不得不使用较弱编码时，就用直接标注与说明尺度的图例来补偿。

- **部分-整体**：单位华夫图，面积编码延误分钟占比，每一格都被标注，73.3 / 26.7 的拆分不靠图例也能读出来。
- **有序与周期**：起飞小时用折线级联图，因为排序条形图会摧毁"日内形状"。
- **分布**：用分位数带与提琴图替代均值柱状图，因为均值落在第 73 百分位。
- **集中度**：Lorenz 曲线，说明最差 1% 的航班承担 25% 的延误分钟。
- **地理**：保留州级方块网格用于全国比较，并列增加一张分级统计地图读取量级。
- **体量**：机场气泡按起飞量定尺寸，配明确尺寸图例。

**有一组对比是刻意做出来的，而不是嘴上说的。** 同一份十二个月的剖面，左边是均值柱状图，右边保留中位数、均值与 p90。左边的柱状图不是稻草人——它用零基线、带数值标注、按时间排序，但它仍无法支撑"中位数从未穿过零"这句话。把两者并排发表，就把编码论证从"主张"变成了"证据"。

**色彩。** 每个原因固定一个颜色，在所有图中保持一致。色板遵循 Okabe 与 Ito（2008），顺序色阶使用 viridis（亮度单调，灰度打印可读）。

**交互。** 沟通层遵循 Shneiderman（1996）任务分类：**先概览、再缩放与筛选、最后按需看细节**。仪表板以全国概览开场，暴露三个筛选器，图表之间联动。

**评估。** 可用性是**测量**出来的，不是宣称出来的。给非专业用户三项任务——找出指定承运人最差的月份、比较两个机场、估计 19:00 起飞的风险——记录完成时间与错误率，附满意度问卷。

## 7. 仓库与可复现性

项目组织为一个**可运行的仓库**：最终报告里的每一张图、每一张表，都由**一条命令**从源数据重新生成，53 个测试钉住数字来源。

```text
Team01-FlightDelay-Project/
  README.md                  目的、环境搭建、运行命令、数据字典入口
  requirements.txt           锁定版本的 Python 依赖
  Makefile                   setup / data / pipeline / figures / dashboard / test
  docs/                      提案、会议纪要、视频脚本、论坛发帖
  src/                       config、io、清洗、特征、归因、建模、绘图
  dashboard/                 app.py、layouts、callbacks、panels/、assets/
  figures/                   01–14，每图对应一个问题，由各阶段重新生成
  outputs/                   tables/ 与 metrics/，供报告引用
  data/                      raw/、interim/、processed/（不纳入 Git）
  tests/                     53 个测试，覆盖数据、分析、图表与图注层
  reports/                   最终报告（report.md）与导出的提交 PDF
```

**运行命令。** 环境搭建 `python -m pip install -r requirements.txt`；`make data` 下载并校验面板；`make pipeline` 跑全部分析阶段；`make dashboard` 本地启动应用；`make test` 跑测试套件。屏幕与报告里的数字来自同一次 `outputs/` 计算。

**版本控制。** 一个共享 GitHub 仓库，每任务一分支，合并前评审。原始与处理后数据不纳入版本控制；校验清单记录报告结果所用的确切文件。
